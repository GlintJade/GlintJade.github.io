2025년 8월부터 2026년 2월까지 IPP 기업실습으로 운영 중인 웹 시스템의 유지보수에 참여했습니다. Spring과 JSP로 만들어진 기존 시스템에 **데이터를 구분하는 키값 2개가 새로 추가**되면서, 이를 화면과 쿼리, 배치 프로그램에 반영하는 작업을 맡았습니다. 이 과정에서 집계 쿼리의 조회 시간을 **0.4초에서 0.1초로** 줄였습니다.

<!-- outline-end -->

### 실습 개요

| 항목 | 내용 |
| --- | --- |
| 기간 | 2025.08 ~ 2026.02 |
| 형태 | IPP 기업실습 |
| 역할 | 풀스택 웹 유지보수 (프론트, 백엔드, SQL, 배치) |
| 기술 스택 | Spring, JSP, XML 쿼리(Mapper), SQL, Quartz |

이미 운영 중인 시스템이라 새로 만드는 것보다 **기존 코드 구조를 먼저 파악하는 일**이 중요했습니다. Spring으로 짜인 프론트·백엔드 코드의 흐름을 따라가며 구조를 익힌 뒤, 그 위에 기능을 추가하는 방식으로 작업했습니다.

### 1. 새 구분 키값 반영 (2025.10.21 ~)

데이터를 나누는 기준이 되는 키값 2개가 새로 추가되었습니다. 사용자가 이 기준으로 데이터를 걸러 볼 수 있도록 여러 화면에 드롭다운박스를 추가하고, 새 화면 3~4개를 만들었습니다.

드롭다운박스 하나를 추가하는 데에도 여러 곳을 함께 고쳐야 했습니다.

- **프론트(JSP)**: 화면에 드롭다운박스를 추가하고, 선택한 값을 조회 조건으로 넘기도록 수정했습니다.
- **백엔드(Spring)**: 드롭다운 목록과 조회에 필요한 API를 추가하고 프론트와 연결했습니다.
- **SQL(XML)**: 외부에서 수신되는 데이터를 확인한 뒤, 기존 SQL문에 새 키값에 대한 JOIN과 조건을 추가했습니다.

### 2. 집계 쿼리 성능 개선 (0.4초 → 0.1초)

새 키값 조건을 넣기 위해 쿼리를 살펴보던 중, 기간별 데이터를 집계하는 쿼리의 구조에서 문제를 발견했습니다.

- 거의 같은 SELECT문이 조건만 바뀐 채 여러 번 반복되고 있었습니다.
- 그 결과들을 다시 많은 수의 JOIN으로 이어 붙이고 있었습니다.
- 여기에 새 키값에 대한 JOIN까지 추가하면 성능 문제가 더 커질 것이라고 판단했습니다.

그래서 쿼리 구조를 바꿨습니다.

1. 반복되던 SELECT문을 하나로 합쳐, 데이터를 한 번만 읽도록 했습니다.
2. 여러 번의 JOIN으로 붙이던 부분을 `CASE WHEN`과 집계함수(`SUM`, `MAX`)를 이용한 방식으로 대체해, JOIN 수를 크게 줄였습니다.

그 결과 조회 시간이 **0.4초에서 0.1초로** 줄었고, 새 키값 조건을 추가한 뒤에도 성능을 유지할 수 있었습니다.

### 3. 알람 배치 프로그램

특정 이벤트가 발생하면 관련 사용자에게 메일로 알려주는 알람 배치 프로그램을 작업했습니다. 스케줄링은 **Quartz**를 사용했고, 서버가 재시작되어도 스케줄 정보가 유지되도록 Persistence 모드로 구성되어 있었습니다.

배치 프로그램에서도 메일을 받을 사용자를 새 키값 기준으로 구분해야 했습니다. 수신자를 조회하는 로직에 새 기준을 반영해, 이벤트가 발생했을 때 해당하는 사용자에게만 메일이 가도록 알람 기능 전반을 수정했습니다.

### 4. 데이터 마이그레이션

개발 서버에서 작업한 데이터를 운영 서버로 옮기는 마이그레이션 작업도 진행했습니다.

### 배운 점

- 운영 중인 시스템은 한 곳을 바꾸면 화면, API, 쿼리, 배치까지 영향이 이어진다는 것을 체감했습니다. 드롭다운박스 하나를 추가하는 일도 데이터 흐름 전체를 이해해야 가능했습니다.
- 기능을 추가하기 전에 기존 쿼리 구조를 먼저 점검한 덕분에, 성능 문제가 커지기 전에 미리 개선할 수 있었습니다.
